# Guard rails on a domain rules

## Overall

When building a domain rules for some businesses, there are such rules that are so obvious, like action that does not make sense and should not happen, we sit between two ideas: put a guard rails on those actions to stay consistent and take off the gun with which the business can try to shot itself, or allow a flexibility which will create a none logical state or action, but that action then can be resolved and as a prestate is needed for the business, whereas with the guards they will have to bypass the system rules and make other creativity compensations.


## Visit

Creating a visit from the moment of booking has a logical straight rule on time and that is a scheduled or reserved visit can not be created before the moment of reservation because in the past we can enter a resolved visit we know the outcome.
But the business maybe wants to backfill that type of data, case: they forget to enter the scheduled visit and now they want that data.

## Solution 

One configuration that is default the guard rails applied, then the admin can re-configured it. And that is for every other feature not just for time and visit creation or state chaging actions.
